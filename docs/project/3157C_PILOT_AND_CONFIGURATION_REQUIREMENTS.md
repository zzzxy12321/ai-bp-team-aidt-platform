
4. 数字员工对截止日期存在一天偏移。

因此本试点结论为：**业务链已跑通，状态治理和跨视图一致性未通过。**

## ⚠️ 试点缺陷

### P0-1：事件状态未持久化

**现象**

- 分析完成后，事件仍为 `Received`，没有稳定变为 `AwaitingConfirmation`。
- 真人确认并创建任务后，事件仍为 `Received`，没有变为 `Confirmed`。
- 页面继续显示“真人确认并创建项目任务”按钮。

**影响**

- 用户不知道事项是否已经处理。
- 可能重复点击确认，只能依赖后端任务唯一约束兜底。
- “待真人确认”指标失真。
- 事件 `AnalysisRunId` 读取为空，影响数字员工运行证据反查。

**疑似根因**

- `SqlEventInboxService.LoadAccessibleEventAsync` 通过 `ApplyEventScope` 的非跟踪查询读取事件。
- 分析和确认逻辑随后修改内存状态，但没有显式更新并保存实体。

**修复要求**

- 分析成功后持久化 `AwaitingConfirmation` 和 `AnalysisRunId`。
- 确认成功后持久化 `Confirmed`。
- 页面按服务端最终状态刷新，不允许已确认事件重复显示确认入口。
- 增加“分析后状态、确认后状态、刷新后状态一致”回归测试。

### P0-2：项目状态未持久化

**现象**

- 通过网页选择“已完成”，页面提示“项目状态已更新”。
- 审计出现 `project.status_changed`，但页面和重新读取仍为“进行中”。

**影响**

- 页面状态与审计证据矛盾。
- 项目无法可靠关闭或进入验收。
- 后续报表、权限和流程条件不可信。

**疑似根因**

- `SqlProjectService.ChangeStatusAsync` 使用非跟踪方式加载项目。
- 修改 `Status/Version` 后没有将实体附着到 EF 跟踪。

**修复要求**

- 项目状态变更后必须持久化主对象状态和版本。
- 状态变更、审计和版本更新必须保持一致。
- 增加“状态变更成功、刷新后仍为新状态”的持久化测试。
- 禁止提示成功但实际主对象未更新。

### P1-1：项目附件关系未自动形成

**现象**

- 上传文件时填写了 `BusinessObjectId`，文件中心可以查到文件。
- 项目详情文件区最初为空。
- 补录 `Attachment / SupportingEvidence` 项目关系后正常展示。

**影响**

- 用户以为文件已经放进项目，项目经理却看不到。
- 证据链依赖人工补录，容易遗漏。

**修复要求**

- 从项目上下文上传附件时，自动创建项目附件证据关系。
- 从事件附件转为项目任务时，自动把事件附件关联到项目。
- 文件中心、项目详情和审计必须使用同一个关联事实。
- 增加“上传一次后三处同时可见”的测试。

### P1-2：截止日期识别偏移一天

**现象**

- 原文“任务截止日期：2025-08-15”被建议为 `2025-08-16 02:00:00`。

**影响**

- 任务可能被错误判断为逾期。
- 自动提醒时间不准。

**修复要求**

- 日期解析按组织时区统一处理。
- 日期识别结果必须保留原文依据。
- 当提取日期和项目结束日期冲突时，前端必须提示人工确认。
- 增加日期、时区、跨日边界单元测试。

## 🧭 产品原则

### 一个平台，多种岗位视图

不建立“财务数据库、采购数据库、经理数据库、研发数据库”等彼此割裂的系统。

正确结构是：

```text
统一身份和权限
 → 统一业务对象和数据账本
 → 角色工作台
 → 流程模板和标准能力包
 → 项目/文件/事件/证据关联
 → 数字员工
```

岗位差异由以下内容实现：

- 可见菜单和视图
- 数据范围
- 动作权限
- 流程模板
- 表单字段
- 节点能力包
- 报表和提醒

### 员工先看到事情，不先看到技术概念

普通员工页面使用“发起事项、待我处理、等待谁处理、附件、截止时间、结果”等业务语言，
不暴露工作流定义 ID、节点代码、TraceId 和数据库字段。

### 配置不等于任意改代码

业务人员配置的是预置能力组合，不是在前端生成新后端代码。

目标是：

- 80% 通过标准能力包和模板配置完成
- 15% 通过参数、规则和页面布局调整完成
- 5% 通过平台团队受控扩展完成
